대상: apps/company-map · 작성일 2026-08-27 · 상태: 설계 승인됨(구현 계획 대기)

1. 목적

QQQ가 직전 최고가 대비 일정 비율 이상 하락한 구간에서는 QLD(나스닥100 2배)를, 그 외에는 QQQ를 매 미국 거래일 일정 금액씩 매수하는 적립식 전략을 company-map 안에서 운용·추적한다. 기존 무한매수법·밸류리밸런싱 VR과 동일한 운용 관리 패턴(계좌 등록 → 워커가 거래일마다 신호 생성 → 주문 기록·제출 → 화면에서 상태 추적)을 따른다.

근거가 된 백테스트(2006-08-28 ~ 2026-08-26, 매 거래일 5만원): 10% 룰 XIRR 27.7% · MDD −52.7%, 15% 룰 26.9% · −50.7%, QQQ 단독 20.3% · −30.3%. 이 설계는 백테스트를 재현하는 것이 아니라 같은 규칙을 실계좌에 앞으로 적용하는 것이 목적이다.

4. 확정된 설계 선택

4.1 매수 주문 방식 — 금액 기반(orderAmount) 시장가 매수

orderType: "MARKET" + orderAmount(달러 금액 문자열) + clientOrderId. price·quantity·timeInForce는 아예 보내지 않는다. 토스 명세가 두 주문 형태를 oneOf로 배타화해서, CreateOrderInput(src/lib/toss/client.ts)이 QuantityOrderInput | AmountOrderInput 유니온이라 둘을 섞으면 타입 레벨에서 컴파일 에러가 난다.

당초 이 절의 결정은 LIMIT / tif: "CLS" LOC 종가매수, 지정가 = 현재가 × (1 + premiumPct/100)였다. 이 결정은 폐기됐다 — 토스 명세의 세 조건이 서로 배타적이기 때문이다: timeInForce: "CLS"는 orderType: "LIMIT"를 요구하고, LIMIT은 소수점 수량을 거부하며("소수점 매수는 orderAmount를 사용하세요"), orderAmount는 orderType: "MARKET" 전용이다. 정수 수량 제약을 없애 매일 잔액 전액을 투입하려면 LOC 종가매수와 소수점 매수 중 하나를 포기해야 했고, 후자를 택했다.

정수 수량 LOC 모델에서는 5만원/거래일 적립으로 QQQ가 약 21거래일에 한 번, QLD가 약 3거래일에 한 번만 체결됐다 — 평상시엔 현금이 계좌에 고이다가 낙폭이 시작되는 순간 그동안 쌓인 잔액이 QLD에 한꺼번에 몰려 들어가는 체계적 왜곡이 있었고, 이는 백테스트가 검증한 "매 거래일 균등 투입"과 어긋났다. 금액 기반 모델은 매 거래일 잔액을 전액 투입하고 센트 단위 절삭분만 다음 거래일로 이월한다 — 대가는 체결가가 종가가 아니라 주문 시점의 장중 시세라는 점이다(방향성 없는 잡음이라 장기적으로는 상쇄되는 것으로 기대한다).

4.2 낙폭 기준 최고가 — DB running peak

계좌 생성 시 200봉 최고 종가로 peakPrice를 자동 시딩하고(생성 폼에서 수동 입력으로 덮어쓸 수 있음), 이후 매 거래일 base 종목의 전일 종가로 갱신한다. 시딩 시점의 200봉(약 10개월) 밖에 진짜 사상 최고가가 있으면 초기 낙폭이 과소평가되므로, 생성 화면에 이 한계를 명시하고 수동 입력을 허용한다.

4.3 임계 비교의 부동소수점 허용오차

pickSymbol(src/lib/dca/peak.ts)의 레버리지 판정은 ratio <= -thresholdPct / 100 + 1e-9로, 반올림 전 낙폭 비율(drawdownRatio)에 1e-9 허용오차를 더해 비교한다. IEEE754에서 90/100 - 1은 정확히 -0.1이 아니라 -0.09999999999999998로 계산되므로, 허용오차 없이 비교하면 낙폭이 임계값에 정확히 도달한 경계 케이스가 false negative로 레버리지 종목을 놓친다. 3장에서 정한 "경계 포함"(≤) 요구사항을 실제로 충족하려면 이 오차 보정이 필수다. 1e-9는 부동소수점 오차(~1e-17)보다 훨씬 크고, 표시용 반올림 경계 케이스(예: −9.996% vs −10%, 차이 ~4e-5)보다는 훨씬 작게 잡아 두 상황이 섞이지 않도록 한다.

5. 데이터 모델

apps/company-map/prisma/schema.prisma의 실제 모델(금액 기반 전환 반영). 기존 VR/무한매수 모델의 명명·매핑 관행(@map snake_case, 문자열 거래일 YYYY-MM-DD)을 그대로 따른다. premiumPct는 삭제됐고, DcaOrder에 amountUsd·clientOrderId가 추가됐으며 tif·price·quantity는 nullable로 바뀌었다(금액 기반 주문에는 이 값들이 없다).

model DcaAccount {
  id              String   @id @default(uuid())
  name            String                                    // 표시용 이름
  baseSymbol      String   @default("QQQ")  @map("base_symbol")
  leverSymbol     String   @default("QLD")  @map("lever_symbol")
  accountSeq      Int?     @map("account_seq")              // 토스 계좌(null=기본계좌)
  thresholdPct    Float    @default(10)     @map("threshold_pct")    // 이 % 이상 하락 시 레버리지
  dailyAmountKrw  Float    @default(50000)  @map("daily_amount_krw") // 거래일당 적립액(원)
  cashKrw         Float    @default(0)      @map("cash_krw")         // 미체결 이월 잔액(원)
  peakPrice       Float    @map("peak_price")                        // base 종목 최고 종가
  peakDate        String   @map("peak_date")
  startDate       String   @map("start_date")
  status          String   @default("active")                // active | paused | stopped
  dryRun          Boolean  @default(true)   @map("dry_run")
  note            String?                                    // 마지막 경고/보류 사유
  lastRunDate     String?  @map("last_run_date")             // 거래일당 1회 보장
  lastAccrualDate String?  @map("last_accrual_date")         // 적립 멱등 마커 (10장 참조)
  createdAt       DateTime @default(now())  @map("created_at")
  updatedAt       DateTime @updatedAt       @map("updated_at")

  orders DcaOrder[]

  @@map("dca_accounts")
}

model DcaOrder {
  id            String   @id @default(uuid())
  accountId     String   @map("account_id")
  tradeDate     String   @map("trade_date")             // US 거래일
  symbol        String                                  // 실제 매수한 종목(QQQ | QLD)
  side          String                                  // BUY 고정
  kind          String                                  // loc_buy 고정 (LOC 폐기 이후에도 문자열은 그대로 — 12장 참조)
  orderType     String   @map("order_type")             // MARKET
  tif           String?                                 // 금액 기반 주문에는 없음
  price         Float?                                  // 주문 시점 참조 시세(감사용). 금액 기반 주문에는 지정가가 없다
  quantity      Float?                                  // 주문 시점 예상 수량(감사용). 실제 수량은 체결 시 결정된다
  amountUsd     Float    @map("amount_usd")             // 주문한 달러 금액 — 금액 기반 주문의 핵심 값
  clientOrderId String?  @map("client_order_id")        // 토스 멱등성 키. dryRun에서는 null
  amountKrw     Float    @map("amount_krw")             // 주문 시 배정한 원화(추정)
  fxRate        Float    @map("fx_rate")                // 주문 시 USD/KRW
  drawdownPct   Float    @map("drawdown_pct")           // 판정에 쓴 낙폭(%) — 감사용
  filledQty     Float?   @map("filled_qty")
  filledPrice   Float?   @map("filled_price")
  filledAt      String?  @map("filled_at")
  tossOrderId   String?  @map("toss_order_id")
  stateApplied  Boolean? @map("state_applied")          // cashKrw 반영 여부(멱등 마커)
  dryRun        Boolean  @map("dry_run")
  status        String                                  // simulated_filled | expired | submitting | submitted | filled | rejected | submit_unknown
                                                         //   submitting: 제출 직전에 만든 뮤텍스 행 / submit_unknown: 제출 결과 미확인(수동 확인 필요)
                                                         //   rejected: 브로커가 HTTP 400/422로 확실히 거절 — 주문 미생성, 잔액 영향 없음
  error         String?
  createdAt     DateTime @default(now()) @map("created_at")

  account DcaAccount @relation(fields: [accountId], references: [id], onDelete: Cascade)

  @@index([accountId, tradeDate])
  @@map("dca_orders")
}

상태 불변식

  • cashKrw는 "아직 주식으로 바뀌지 않은 원화 적립 잔액"이다. 거래일마다 dailyAmountKrw가 더해지고, 체결이 확정된 순간에만 차감된다. 주문 제출은 잔액을 건드리지 않는다 — 미체결 시 원복 로직이 필요 없어진다. dryRun 주문은 금액 기반 시장가라 생성 즉시 체결로 기록되므로, 같은 실행 안에서 바로 차감된다(6장 참조) — LIVE만 정산을 별도 단계로 기다린다.
  • 차감액(원) = filledPrice × filledQty × 주문에 기록된 fxRate. 체결 시점 환율이 아니라 주문 시점 환율을 쓴다(근사). amountKrw는 주문 시점의 추정치일 뿐 이 차감액의 권위가 아니다.
  • 보유수량은 상태로 저장하지 않고 체결 이력에서 파생한다(VR deriveHolding과 동일). 매수 전용이라 주문 계산에는 쓰이지 않고 화면 표시 전용이다.
  • 모든 상태 변경은 stateApplied·lastRunDate·"당일 주문 존재" 3중 가드로 멱등하다. 브로커 제출 자체는 추가로 clientOrderId 멱등성 키로 보호된다(6장 참조) — DB 유니크 제약(@@unique([accountId, tradeDate]))은 아직 두지 않았다(열린 후속 과제, 12장 참조). 세 가드가 모두 "그 거래일 안"에서만 작동하므로, 이전 거래일의 미해결 LIVE 주문은 별도 가드(6장 ⑤')가 막는다.

6. 실행 흐름 (runDca)

거래일당 1회. 순서 불변식은 ① LIVE 체결 정산 → ② 잔액 반영 → ③ 적립 → ④ peak 갱신 → ⑤ 종목 선택 → ⑤' 이전 거래일 미해결 주문 가드 → ⑥ 주문 접수 창 확인 → ⑦ 주문 금액 계산 → ⑧ 기록·제출이다(run-dca.ts 파일 첫머리 주석). 실패하면 lastRunDate를 갱신하지 않아 다음 폴에서 자동 재시도한다(VR·무한매수 v4와 동일한 blocked 패턴). 주문이 금액 기반 시장가로 바뀌면서 dryRun의 2단계 정산이 사라졌다 — 이전에는 dryRun 주문을 simulated로 만들고 다음 거래일 일봉으로 체결 여부를 판정했지만, 시장가는 즉시 체결되므로 이제 dryRun 주문은 ⑧ 단계에서 생성과 동시에 simulated_filled로 기록되고 같은 실행 안에서 차감까지 끝난다. LIVE만 여전히 별도 정산(①)을 기다린다.

kill switch는 거래만 멈춘다 — 장부는 멈추지 않는다. DCA_DISABLED=1이면 runDca는 blocked: "disabled"를 반환하고 적립·종목 선택·주문 기록을 하지 않으며 lastRunDate도 갱신하지 않는다. 다만 ①·②(체결 정산·잔액 반영)는 그 전에 이미 실행된다 — 이 두 단계는 거래가 아니라 이미 나간 주문을 장부에 따라잡는 기록 작업이다. 뒤에 두면 체결이 submitted로 떠 있는 채 계좌를 멈추고 설정 폼에서 cashKrw를 손으로 보정한 뒤 재개하는 순간 같은 체결이 두 번 차감된다. 같은 이유로 status !== "active"(일시정지·중지) 검사도 ①·② 뒤에 있다. 자세한 이유는 10장 참조. 한계: worker/dca-loop.ts는 status: "active" 계좌만 폴하므로, 일시정지 상태에서의 자동 정산은 화면의 "지금 실행"에서만 일어난다(킬 스위치 경로는 워커에서도 정산된다).
  1. ① LIVE 체결 정산 — settleLiveOrders. 대상은 계좌 모드가 아니라 주문 행의 dryRun: false, status: "submitted"이다(dryRun 주문은 생성 시점에 이미 체결로 기록되므로 여기서 볼 것이 없다 — 계좌 모드로 분기하지 않는 이유는 LIVE→dryRun 전환 후 남은 submitted 행이 정산을 못 받고 얼어붙는 것을 막기 위함). getOrders(accountSeq, {status:"CLOSED", symbol, from})로 대조해 filled / expired로 확정한다. 브로커 주문 하나는 주문 행 하나만 정산할 수 있다 — clientOrderId 멱등성 때문에 뮤텍스를 놓친 동시 제출 두 건이 토스에서 같은 tossOrderId로 합쳐질 수 있는데, 그대로 두면 두 행이 같은 체결에 각각 매칭돼 한 번의 매수가 두 번 차감된다. 그래서 이미 소비된 tossOrderId 집합을 (이미 정산된 filled 행에서도 미리 시딩해) 추적하고, 두 번째 행은 expired + "중복 제출이 같은 브로커 주문으로 합쳐짐" 에러로 닫아 차감하지 않는다. 이 소비 집합은 계좌 범위다 — 계좌 간 clientOrderId 충돌(앞 16자 truncation)까지는 이 집합이 막지 못한다. 결국 64비트 충돌 확률에 기댄다(12장 참조). 실패하면 blocked로 멈추고 다음 폴에서 재시도한다.
  2. ② 잔액 반영 — applyPendingFills. stateApplied가 아직 아닌 체결(simulated_filled 또는 filled)을 순수 함수 applyFills로 계산한 뒤, 그 델타만큼 cashKrw를 Prisma decrement로 차감하고 마커를 세운다. applyFills가 건너뛰는 행(filledQty/filledPrice가 null, 또는 fxRate가 0 이하·비정상)은 stateApplied를 세우지 않고 보류로 남긴다 — 세워버리면 그 금액이 차감 없이 영구히 잔액에서 누락되고 재시도 기회도 사라지기 때문이다. 조회 → 계좌 조회 → 쓰기 사이에 다른 실행이 끼면 같은 체결을 두 번 차감할 수 있으므로, 각 행의 마커를 조건부 updateMany(아직 반영되지 않은 행으로 범위 한정)로 먼저 세우고 count === 1인 행만 차감한다 — 뒤늦게 들어온 실행의 쓰기는 무동작이 된다. 청구(마커)와 차감은 하나의 인터랙티브 $transaction에 묶여 있어, 차감이 실패하면 마커도 함께 롤백된다(마커만 남으면 그 금액이 영구히 누락된다). 절대값 쓰기가 아니라 상대 증감이므로 동시에 다른 실행이 적립을 반영 중이어도 서로를 덮어쓰지 않는다.
  3. ③ 적립 — lastAccrualDate !== tradeDate일 때만 순수 함수 accrue로 계산한 델타를 cashKrw에 Prisma increment로 더하고 lastAccrualDate = tradeDate로 갱신한다. 이후 단계가 보류되어도 재적립되지 않는다(10장 참조). 여기서도 절대값이 아닌 상대 증감을 써서 state.ts의 순수 함수가 계산의 유일한 근거로 남는다.
  4. ④ peak 갱신 — base 종목의 전일 종가 prevClose가 peakPrice보다 크면 peakPrice/peakDate를 갱신. 전일 종가를 못 구하면 실패 사유를 담은 문자열(조회 자체가 실패했으면 전일 종가 조회 실패: ..., 조회는 됐지만 데이터가 없으면 전일 종가 미확보 — 재시도 대기)을 blocked·note에 그대로 남기고 보류(10장 참조).
  5. ⑤ 종목 선택 — drawdown = prevClose / peakPrice - 1. drawdown ≤ -thresholdPct/100 + 1e-9이면 leverSymbol, 아니면 baseSymbol(허용오차는 4.3절 참조).
  6. ⑤' 이전 거래일 미해결 주문 가드 — 이 계좌의 dryRun: false 행 중 이전 거래일이면서 상태가 submitting·submitted·submit_unknown인 것이 하나라도 있으면, 적립·peak 갱신은 그대로 둔 채 block(...)으로 주문만 막는다. 세 멱등 가드(lastAccrualDate·stateApplied·당일 주문 수)는 전부 그 거래일 안에서만 작동해, 어제 결과를 모르는 주문이 남아 있어도 오늘 주문이 그대로 나간다 — 그 주문이 체결됐다면 cashKrw가 아직 차감되지 않아 오늘 주문이 이틀치 잔액으로 나간다(1회분 과매수. 그 행이 정산되면 잔액은 다시 수렴하므로 누적되지는 않는다). block이라 lastRunDate를 소진하지 않고 note를 매 폴마다 다시 세운다 — 장부와 브로커가 어긋났다는 유일한 화면 신호인 그 note가 다음 성공·창닫힘 실행에 지워지지 않는 효과도 함께 얻는다. 해소하려면 토스 앱에서 체결 여부를 확인하고 cashKrw를 보정한 뒤 그 행의 상태를 바꿔야 하는데, 상태를 바꾸는 UI가 없어 DB 직접 편집이 필요하다(12장 참조).
  7. 중복 방지 (1차) — 해당 계좌·거래일에 이미 주문 행이 있으면 아래 창 확인·시세·환율 조회를 아예 건너뛰고 lastRunDate만 갱신한 뒤 noOrderReason: "already_ordered"로 종료한다. 네트워크 호출 전에 먼저 걸러 불필요한 왕복을 없앤다. 이 경로는 note를 지우지 않는다 — 직전 실행이 남긴 submit_unknown 경고가 다음 거래일에 조용히 사라지면 화면에 그 신호가 아예 남지 않는다.
  8. ⑥ 주문 접수 창 확인 — isAmountOrderWindowOpen()(src/lib/dca/market-window.ts). 금액 기반 주문은 정규장 시작부터 종료 1시간 전까지만 접수된다. "창이 닫혔다"와 "확인하지 못했다"를 구분한다 — 전자(창 닫힘)는 그날 재시도가 무의미하므로 lastRunDate를 소진시키고 note에 "정규장 종료 1시간 전 경과"를 남기고 noOrderReason: "window_closed"로 끝난다. 후자(캘린더 조회 자체의 실패)는 isAmountOrderWindowOpen이 throw하며, 호출자는 이를 block(...)으로 넘겨 lastRunDate를 건드리지 않는다 — 둘을 false로 합치면 토스 토큰 재발급 실패 한 번(활성 토큰이 계좌당 1개뿐이라 흔한 모드)이 그날 매수를 통째로 날리기 때문이다.
  9. ⑦ 주문 금액 계산 — planAmountBuy({cashKrw, fxRate})가 Math.floor(cashKrw/fxRate × 100)/100로 센트 단위까지 환산해 잔액 전액을 투입 금액으로 정한다(정수 수량 제약이 없으므로 상한이 없다). 환산액이 1센트 미만이면 null을 반환하고, 호출자는 주문 없이 lastRunDate만 갱신 + note = null + noOrderReason: "below_min_amount"로 마친다. estimateQuantity(amountUsd, price)로 표시·감사용 예상 수량을 함께 계산하지만, 실제 체결 수량은 토스가 주문 시점 시세로 정한다.
  10. LIVE 예수금 확인 — LIVE 계좌만. getBuyingPower(accountSeq,"USD")로 매수가능금액을 받아 !(buyingPower >= plan.amountUsd)로 판정한다(fail-closed). buyingPower < plan.amountUsd로 쓰면 응답 필드 누락·개편으로 NaN이 왔을 때 비교가 false가 되어 검사 없이 실주문이 나간다. 부족하거나 값이 유한하지 않으면 blocked + note로 보류하고 주문 행은 만들지 않는다 — 이 시점에 행이 없어야 같은 거래일 안에 다음 폴에서 재시도할 수 있다. 이 조회를 아래 재확인보다 먼저 두는 이유도 같은 맥락이다: 재확인과 주문 행 생성 사이에 네트워크 왕복이 끼면 중복 주문 창이 그만큼 다시 넓어진다.
  11. 중복 방지 (2차, 재확인) — 1차 체크 이후 창 확인·시세·환율·예수금 조회(네트워크 왕복) 동안 동시 실행이 끼어들 여지가 있으므로, 주문 행을 만들기 직전에 같은 카운트를 한 번 더 실행한다. 걸리면 마찬가지로 lastRunDate만 갱신하고(note는 유지) noOrderReason: "already_ordered"로 종료. 재확인 직후에 오는 것은 로컬 SQLite 쓰기 1회(주문 행 생성)뿐이므로 dryRun·LIVE 양쪽 모두 창이 그 한 번의 쓰기로 좁혀지지만, DB 제약은 아니다 — 그 좁은 창이 뚫려도 clientOrderId가 2선 방어로 남는다(12장 참조).
  12. ⑧ 기록 / 제출 — dryRun이면 status: "simulated_filled" 행 1건을 사이징에 쓴 시세로 즉시 체결 기록하고, 같은 실행 안에서 applyPendingFills를 다시 호출해 차감까지 끝낸다. LIVE는 제출 전에 status: "submitting" 행을 먼저 만들어 그 행 자체를 뮤텍스로 쓰고, clientOrderId = makeClientOrderId(accountId, tradeDate)(계좌 앞 16자 + 거래일, 최대 29자)를 실어 createOrder가 성공하면 같은 행을 status: "submitted" + tossOrderId로 갱신한다. 제출이 throw하면 예외를 둘로 가른다: 토스가 HTTP 400/422로 되돌려준 응답은 주문이 생성되지 않은 것이 확정이므로 status: "rejected" + 실제 사유로 남기고(lastRunDate 소진, noOrderReason: "rejected", 단 422 amount-order-outside-regular-hours는 window_closed로 되돌린다), 그 밖의 예외는 실패로 단정하지 않고 status: "submit_unknown" + error로 남긴다(아래 블록쿼트). (kill switch는 이 단계 전에 이미 걸러진다 — 위 블록쿼트 참조)
  13. 정상 완료 경로는 lastRunDate = tradeDate, note = null로 마무리한다. 중복 방지 1·2차, 창 닫힘, 1센트 미만 경로는 lastRunDate만 갱신하고(창 닫힘·1센트 미만은 note도 갱신, 중복 방지는 note 유지) 대응하는 noOrderReason을 결과에 싣는다.
제출 실패는 "실패"가 아니라 "미확인"이다. tossFetch는 POST /api/v1/orders를 포함한 모든 호출에 10초 AbortSignal.timeout을 건다. 토스가 주문을 접수했는데 응답만 늦어도 submitOrder는 throw한다. 이때 failed로 기록하면 그 주문은 시장가로 체결되는데 settleLiveOrders는 submitted만 조회하므로 영구히 정산되지 않고, cashKrw가 차감되지 않아 다음 거래일 주문이 부풀려진 잔액으로 나간다. 그래서 별도 상태 submit_unknown + error 문구를 남기고, 계좌 note에 주문 제출 결과 미확인 — 토스 앱에서 체결 여부를 직접 확인하세요: ...를 세워 카드에 경고 배지로 띄운다. lastRunDate는 갱신한다 — 여기서 자동 재시도하는 것이야말로 진짜 이중 매수를 만든다. 브로커 자동 대조는 하지 않는다: DcaRunDeps에 OPEN 주문 목록 조회가 없고, 추가하는 것은 이번 범위 밖이다. 다만 "미확인"이 기본값일 뿐 전부는 아니다 — 토스가 HTTP 400(요청 자체가 유효하지 않음: invalid-request·금액 최소/최대 위반 등)이나 422(처리 불가)로 되돌려준 응답은 주문이 만들어지지 않은 것이 확정이고 cashKrw도 정확하므로, rejected로 적고 사람 확인을 요구하지 않는다. 이것까지 submit_unknown으로 적으면 거래정지 종목 같은 결정적 400이 매 거래일 "브로커를 확인하라" 경고를 만들고, ⑤' 가드에 걸려 있지도 않은 주문 때문에 매일 주문이 막힌다. 반대로 타임아웃·401·403·5xx·429는 주문이 생겼을 수 있으므로 보수적으로 미확인을 유지한다. 판별은 classifySubmitFailure가 예외의 형태(name === "TossApiError" + status/code)로 한다 — run-dca는 DcaRunDeps 뒤에서 브로커 구현을 모르는 순수 오케스트레이터라 client.ts를 값으로 import하지 않는다(테스트가 실제 TossApiError로 이 결합을 붙잡는다). 이 분기 덕분에 ⑥의 창 확인 이후 시세·환율·예수금 조회 사이에 마감을 넘겨 토스가 422 amount-order-outside-regular-hours로 거절하는 경우도 이제 submit_unknown이 아니라 window_closed로 안내된다.

12. 가정과 한계

  • 배당 재투자 미반영 — 백테스트는 수정주가를 썼지만 실운용은 현금 배당이 계좌에 쌓인다. QQQ 배당수익률 ~0.5% 수준의 괴리.
  • 기존 보유분은 교체하지 않는다 — 신규 적립금의 매수 종목만 바뀐다. 백테스트 조건과 동일.
  • peak 시딩의 한계 — 토스 200봉(약 10개월) 내 최고 종가만 확인 가능. 진짜 사상 최고가가 그 밖에 있으면 초기 낙폭이 과소평가되어 QLD 구간을 놓친다. 생성 폼에서 수동 입력으로 보정한다.
  • 종가 vs 수정주가 — peak과 낙폭 판정 모두 토스 원종가(전일 종가) 기준. 백테스트의 수정주가 기준과 미세하게 다르다.
  • 체결가는 이제 종가가 아니라 장중 시장가 — orderAmount는 MARKET 전용이라 timeInForce: "CLS"(종가매수)와 공존할 수 없다(4.1절). peak·낙폭 판정은 여전히 전일 종가를 쓰지만 실제 매수가는 그날 실행 시점의 장중 시세이므로, 백테스트가 가정한 종가 체결과 개별 거래일 단위로는 괴리가 있다(방향성 없는 잡음이라 누적으로는 상쇄될 것으로 기대한다).
  • 환율 근사 — 체결 차감액을 주문 시점 환율로 환산한다. 실제 원화 체결 원가와 소폭 차이.
  • 보유 정합성 대조 없음 — 같은 토스 계좌에서 다른 경로로 QQQ/QLD를 매매하면 화면의 보유수량(체결 이력 파생)이 실보유와 어긋난다. 주문 계산은 잔액만 쓰므로 주문 안전성에는 영향이 없다.
  • 적립 누락 보정 없음 — 워커가 꺼져 있던 거래일에는 적립이 일어나지 않고, 지난 거래일을 소급 적립하는 로직도 없다. 설정 폼에서 cashKrw를 직접 수정해 보정한다.
  • LIVE는 매수만 — 매도 경로가 없으므로 손절·익절은 수동이다.
  • 금액 기반 주문 접수 창(정규장 종료 1시간 전)과 제출 사이의 시차 — ⑥ 창 확인을 통과한 뒤에도 시세·환율·예수금 조회(LIVE)가 끼어 있다(6장). 이 시차 안에 마감을 넘기면 토스가 실제로 422 amount-order-outside-regular-hours로 거절할 수 있다. 시차 자체는 아직 좁혀지지 않았지만, 그 결과는 이제 submit_unknown이 아니라 status: "rejected" + noOrderReason: "window_closed"로 기록돼 사전 확인(⑥)과 같은 안내를 준다 — "명백히 창이 닫혀서 거절됨"과 "미확인 제출"이 더 이상 섞이지 않는다.
  • 동시 실행 시 당일 중복 주문 가능성 — clientOrderId 멱등성으로 대부분 닫혔다 — "지금 실행"은 Next 서버 프로세스에서, dca-loop는 별도 워커 프로세스에서 같은 SQLite 파일에 붙는다. 로컬 뮤텍스(LIVE도 제출 전에 주문 행을 먼저 만들고 예수금 조회를 재확인보다 앞으로 옮김, 6장)로 재확인~행 생성 사이가 로컬 SQLite 쓰기 1회로 좁혀졌고, 그 좁은 창이 뚫려 두 프로세스가 같은 계좌·같은 거래일에 동시 제출해도 clientOrderId(계좌·거래일마다 결정적으로 생성, 토스가 10분간 동일 키 요청에 이전 결과를 그대로 반환)가 브로커 쪽에서 두 요청을 같은 주문으로 묶어 준다. settleLiveOrders는 소비된 tossOrderId 집합(이미 filled인 행에서도 미리 시딩)으로 그렇게 합쳐진 주문을 두 행이 각각 정산해 이중 차감하는 것도 막는다(6·11장). 남은 위험: 이 소비 집합은 계좌 범위라 계좌 간 충돌은 막지 못한다 — 방어는 결국 clientOrderId에 쓰는 계좌 id 앞 16자(64비트) 충돌 확률에 기댄다(무시할 수준이지만 0은 아니다). 데이터베이스 유니크 제약(@@unique([accountId, tradeDate]))은 아직 두지 않았다 — 아래 항목 참조.
  • cashKrw 절대값 쓰기 (남은 위험은 좁아졌다) — updateDcaSettings는 cashKrw·peakPrice를 절대값으로 덮어쓰는 반면 runDca는 상대 증감(increment/decrement)만 쓴다. 설정 폼은 마운트 시점의 문자열을 useRef로 보관하고 사용자가 실제로 고친 필드만 patch에 담으므로(updateDcaSettings는 undefined 키를 건너뛴다), 폼을 열어둔 사이 워커가 반영한 적립·체결 차감·peak 갱신이 손대지 않은 필드의 옛 스냅샷으로 덮이는 일은 없다. 남은 위험은 사용자가 의도적으로 잔액을 보정해 저장하는 그 순간에 실행이 겹치는 경우뿐이다 — 이때는 절대값 쓰기가 그 사이 반영된 증감을 덮는다. 잔액 보정은 정규장 밖(워커가 실행하지 않는 시간)에 하는 것이 안전하다. 부수적으로, 폼에서 cashKrw 입력을 비우면 Number("")가 0이라 updateDcaSettings가 이를 유효한 cashKrw: 0으로 받아들인다(입력 검증을 통과) — 기존부터 있던 동작이며 이번 전환의 범위 밖이다.
  • @@unique([accountId, tradeDate])는 열린 후속 과제다 (이 문서의 이전 버전은 "폐기"라고 잘못 적었다) — 중복 실주문의 근본 가드는 DB 제약이 아니라 토스 쪽 clientOrderId 멱등성으로 닫혔고(위 항목), 그렇게 합쳐진 주문을 두 행이 각각 정산해 이중 차감하는 것도 settleLiveOrders의 소비된 tossOrderId 추적이 막는다. 그래서 제약은 필수가 아니다. 하지만 유해하지도 않다 — 이전 버전이 근거로 든 "submit_unknown 이후 같은 키로 재시도하는 것이 복구 메커니즘"이라는 서술은 코드에 존재하지 않는 경로였다(그 서술은 바로 다음 항목의 "자동 대조는 범위 밖이고 사람이 수동 확인해야 한다"와도 모순됐다): submit_unknown이면 lastRunDate가 소진되고, 그걸 지워도 당일 주문 수 가드가 already_ordered로 막으며, makeClientOrderId가 결정적이라는 사실만으로 재제출이 일어나지는 않는다. 현재 모든 코드 경로(dryRun·LIVE 제출·rejected·submit_unknown)는 계좌·거래일당 정확히 1행만 만들므로 제약을 걸어도 정상 흐름이 깨지지 않는다. 마이그레이션은 이번 범위에서 실행하지 않는다.
  • 미해결 제출 상태는 사람이 닫아야 한다 (LIVE 전환 전 반드시 인지) — 주문 이력에 submit_unknown(제출이 throw — 타임아웃이면 브로커는 접수했을 수 있고, 마감 직전이면 위 422일 수도 있다) 또는 submitting(제출 도중 프로세스 중단)이 보이면, 토스 앱에서 그 거래일의 실제 체결 여부를 직접 확인해야 한다. 체결됐다면 그 주문은 설계상 자동 정산 대상에서 영구히 제외된다(settleLiveOrders는 status: "submitted"만 본다 — submit_unknown은 대상이 아니다) — 설정 폼에서 cashKrw를 체결금액만큼 직접 줄여야 한다. 이 상태가 이전 거래일에 남아 있으면 ⑤' 가드가 신규 주문을 막고(적립·peak 갱신은 계속된다) 매 폴마다 note를 다시 세우므로, 경고 배지가 다음 성공 실행에 지워지던 문제도 함께 닫혔다. 해소 방법의 한계: 주문 상태를 expired 등으로 바꾸는 UI가 없어, 가드를 풀려면 prisma studio나 sqlite로 dca_orders.status를 직접 고쳐야 한다. 그때까지 그 계좌는 매수를 멈춘다(안전 방향이지만 사람의 개입이 필요하다). 브로커 대조 자동화(OPEN 주문 조회)는 DcaRunDeps에 없고 이번 범위 밖이다.
  • 시뮬레이션 → LIVE 전환 후의 잔액 괴리 — dryRun 주문은 이제 생성 즉시 체결·차감되므로(6장), 전환 이후에 뒤늦게 정산되며 잔액을 건드리는 "밀린 시뮬레이션 행"은 더 이상 생기지 않는다. 다만 근본 원인은 남아 있다 — cashKrw는 그 계좌가 dryRun이었던 기간 동안의 가상 매수 차감을 누적한 값이고, 그 매수는 실제 브로커 현금을 쓰지 않았다. LIVE로 전환한 뒤에도 이 누적 차감분은 그대로 남아 있으므로 추적 잔액이 실제 증권계좌 현금과 다를 수 있다(보유·평가액 표시는 현재 계좌 모드와 같은 체결만 집계하므로 화면상의 보유수량 자체는 혼입되지 않는다). 리셋 로직은 넣지 않았다 — 전환 전에 필요하면 설정 폼에서 cashKrw를 실제 예수금에 맞춰 보정할 것.
  • 체결 시각이 장 초반에 몰린다 (위 "장중 시장가" 항목의 단서) — worker/dca-loop.ts는 프로세스 시작 시각 기준 15분 고정 간격으로 폴하고, 창 판정(isWindowOpenAt)은 nowMs >= open이라 개장 순간을 포함한다. 따라서 실제 주문은 사실상 매일 개장 후 0~15분 안에 나간다. 위 항목이 기대한 "종가 대비 방향성 없는 잡음이라 누적으로 상쇄된다"는 가정은 장 초반에서 덜 성립한다 — 개장 직후는 스프레드가 가장 넓고 변동성이 크다. 체결 시각을 분산시키거나 특정 시각대를 고르는 로직은 넣지 않았다.
  • 이 브랜치의 마이그레이션은 비어 있지 않은 테이블에 재적용할 수 없다 — 20260827221805_dca_amount_based_orders는 SQLite 테이블 재정의(CREATE new_ → INSERT ... SELECT → DROP → RENAME) 방식인데, 새로 추가된 amount_usd가 NOT NULL이면서 INSERT ... SELECT 컬럼 목록에 없다. 이미 적용이 끝난 현재 DB에는 영향이 없고, 마이그레이션 이전 시점의 백업(dca_orders에 행이 있는 상태)을 복원해 다시 적용하는 경우에만 실패한다. 그 경우 amount_usd에 기본값을 넣도록 마이그레이션을 손봐야 한다. 마이그레이션 자체는 수정하지 않았다(이미 적용된 파일을 바꾸면 체크섬이 어긋난다).
  • 실행 1회당 캘린더를 두 번 받는다 — 워커는 usRegularTradeDate()로 세션을 확인하고, 그 뒤 runDca의 ⑥이 isAmountOrderWindowOpen()으로 같은 캘린더를 다시 받는다(src/가 worker/를 import하지 않는 관행 때문에 판정이 두 곳에 복제돼 있다). 캐시가 없어 매 폴마다 토스 호출이 한 번 더 나가고, 토스는 클라이언트당 활성 토큰이 1개뿐이라 이 여분의 호출이 토큰 재발급 경합(token thrashing)을 늘린다 — 곧 ⑧ 제출이 10초 타임아웃에 걸릴 확률, 즉 submit_unknown과 ⑤' 가드 발동 확률을 함께 높인다. 고치려면 캘린더를 DcaRunDeps로 흘려보내야 해서 이번 범위 밖이다.
  • DcaOrder.kind는 여전히 "loc_buy" 문자열을 쓴다 — LOC 종가매수가 금액 기반 시장가로 바뀐 뒤에도 이 컬럼의 값은 바뀌지 않았다. 어떤 코드도 이 컬럼을 읽지 않는다 — 감사용으로만 쓰는 write-only 값이라 실행에는 영향이 없다. 값·스키마 주석·기존 행을 함께 맞추는 정리가 필요해 후속 과제로 남긴다.
