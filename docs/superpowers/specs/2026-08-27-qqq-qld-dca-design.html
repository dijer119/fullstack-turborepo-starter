QQQ·QLD 적립식 전략 설계

대상: apps/company-map · 작성일 2026-08-27 · 상태: 설계 승인됨(구현 계획 대기)

1. 목적

QQQ가 직전 최고가 대비 일정 비율 이상 하락한 구간에서는 QLD(나스닥100 2배)를, 그 외에는 QQQ를 매 미국 거래일 일정 금액씩 매수하는 적립식 전략을 company-map 안에서 운용·추적한다. 기존 무한매수법·밸류리밸런싱 VR과 동일한 운용 관리 패턴(계좌 등록 → 워커가 거래일마다 신호 생성 → 주문 기록·제출 → 화면에서 상태 추적)을 따른다.

근거가 된 백테스트(2006-08-28 ~ 2026-08-26, 매 거래일 5만원): 10% 룰 XIRR 27.7% · MDD −52.7%, 15% 룰 26.9% · −50.7%, QQQ 단독 20.3% · −30.3%. 이 설계는 백테스트를 재현하는 것이 아니라 같은 규칙을 실계좌에 앞으로 적용하는 것이 목적이다.

2. 범위

  • 포함: 새 메뉴 항목(밸류리밸런싱 VR 아래), 계좌 CRUD, 거래일별 자동 실행 워커 루프, dryRun 가상 체결, LIVE 실주문 제출, 주문 이력·상태 화면.
  • 제외: 매도·리밸런싱 로직(전략상 매도 없음), 과거 데이터 백테스트 시뮬레이터, 세금·환전 스프레드 계산.

4. 확정된 설계 선택

4.1 매수 주문 방식 — LOC 종가매수

LIMIT / tif: "CLS", 지정가 = 현재가 × (1 + premiumPct/100). 백테스트가 종가 기준이므로 종가 체결이 가장 근접하고, dryRun 판정이 기존 judgeDryFill과 그대로 맞물린다. 장중 프리미엄을 넘겨 급등하면 미체결되고, 배정 원화는 그대로 남아 다음 거래일에 재시도된다.

4.2 낙폭 기준 최고가 — DB running peak

계좌 생성 시 200봉 최고 종가로 peakPrice를 자동 시딩하고(생성 폼에서 수동 입력으로 덮어쓸 수 있음), 이후 매 거래일 base 종목의 전일 종가로 갱신한다. 시딩 시점의 200봉(약 10개월) 밖에 진짜 사상 최고가가 있으면 초기 낙폭이 과소평가되므로, 생성 화면에 이 한계를 명시하고 수동 입력을 허용한다.

4.3 임계 비교의 부동소수점 허용오차

pickSymbol(src/lib/dca/peak.ts)의 레버리지 판정은 ratio <= -thresholdPct / 100 + 1e-9로, 반올림 전 낙폭 비율(drawdownRatio)에 1e-9 허용오차를 더해 비교한다. IEEE754에서 90/100 - 1은 정확히 -0.1이 아니라 -0.09999999999999998로 계산되므로, 허용오차 없이 비교하면 낙폭이 임계값에 정확히 도달한 경계 케이스가 false negative로 레버리지 종목을 놓친다. 3장에서 정한 "경계 포함"(≤) 요구사항을 실제로 충족하려면 이 오차 보정이 필수다. 1e-9는 부동소수점 오차(~1e-17)보다 훨씬 크고, 표시용 반올림 경계 케이스(예: −9.996% vs −10%, 차이 ~4e-5)보다는 훨씬 작게 잡아 두 상황이 섞이지 않도록 한다.

5. 데이터 모델

apps/company-map/prisma/schema.prisma에 모델 2개를 추가한다. 기존 VR/무한매수 모델의 명명·매핑 관행(@map snake_case, 문자열 거래일 YYYY-MM-DD)을 그대로 따른다.

model DcaAccount {
  id             String   @id @default(uuid())
  name           String                                   // 표시용 이름
  baseSymbol     String   @default("QQQ")  @map("base_symbol")
  leverSymbol    String   @default("QLD")  @map("lever_symbol")
  accountSeq     Int?     @map("account_seq")             // 토스 계좌(null=기본계좌)
  thresholdPct   Float    @default(10)     @map("threshold_pct")    // 이 % 이상 하락 시 레버리지
  dailyAmountKrw Float    @default(50000)  @map("daily_amount_krw") // 거래일당 적립액(원)
  premiumPct     Float    @default(5)      @map("premium_pct")      // LOC 지정가 프리미엄 %
  cashKrw        Float    @default(0)      @map("cash_krw")         // 미체결 이월 잔액(원)
  peakPrice      Float    @map("peak_price")                        // base 종목 최고 종가
  peakDate       String   @map("peak_date")
  startDate      String   @map("start_date")
  status         String   @default("active")               // active | paused | stopped
  dryRun         Boolean  @default(true)   @map("dry_run")
  note           String?                                   // 마지막 경고/보류 사유
  lastRunDate    String?  @map("last_run_date")            // 거래일당 1회 보장
  lastAccrualDate String? @map("last_accrual_date")        // 적립 멱등 마커 (10장 참조)
  createdAt      DateTime @default(now())  @map("created_at")
  updatedAt      DateTime @updatedAt       @map("updated_at")

  orders DcaOrder[]

  @@map("dca_accounts")
}

model DcaOrder {
  id           String   @id @default(uuid())
  accountId    String   @map("account_id")
  tradeDate    String   @map("trade_date")
  symbol       String                            // 실제 매수한 종목(QQQ | QLD)
  side         String                            // BUY 고정
  kind         String                            // loc_buy 고정
  orderType    String   @map("order_type")       // LIMIT
  tif          String                            // CLS
  price        Float                             // LOC 지정가(상한)
  quantity     Float
  amountKrw    Float    @map("amount_krw")       // 주문 시 배정한 원화(추정)
  fxRate       Float    @map("fx_rate")          // 주문 시 USD/KRW
  drawdownPct  Float    @map("drawdown_pct")     // 판정에 쓴 낙폭(%) — 감사용
  filledQty    Float?   @map("filled_qty")
  filledPrice  Float?   @map("filled_price")
  filledAt     String?  @map("filled_at")
  tossOrderId  String?  @map("toss_order_id")
  stateApplied Boolean? @map("state_applied")    // cashKrw 반영 여부(멱등 마커)
  dryRun       Boolean  @map("dry_run")
  status       String                            // simulated | simulated_filled | expired | submitting | submitted | filled | submit_unknown
                                                 //   submitting: 제출 직전에 만든 뮤텍스 행 / submit_unknown: 제출 결과 미확인(수동 확인 필요)
  error        String?
  createdAt    DateTime @default(now()) @map("created_at")

  account DcaAccount @relation(fields: [accountId], references: [id], onDelete: Cascade)

  @@index([accountId, tradeDate])
  @@map("dca_orders")
}

상태 불변식

  • cashKrw는 "아직 주식으로 바뀌지 않은 원화 적립 잔액"이다. 거래일마다 dailyAmountKrw가 더해지고, 체결이 확정된 순간에만 차감된다. 주문 제출은 잔액을 건드리지 않는다 — 미체결 시 원복 로직이 필요 없어진다.
  • 차감액(원) = filledPrice × filledQty × 주문에 기록된 fxRate. 체결 시점 환율이 아니라 주문 시점 환율을 쓴다(근사).
  • 보유수량은 상태로 저장하지 않고 체결 이력에서 파생한다(VR deriveHolding과 동일). 매수 전용이라 주문 계산에는 쓰이지 않고 화면 표시 전용이다.
  • 모든 상태 변경은 stateApplied·lastRunDate·"당일 주문 존재" 3중 가드로 멱등하다.

6. 실행 흐름 (runDca)

거래일당 1회. 실패하면 lastRunDate를 갱신하지 않아 다음 폴에서 자동 재시도한다(VR·무한매수 v4와 동일한 blocked 패턴).

kill switch는 아무것도 하지 않는다. DCA_DISABLED=1이면 runDca는 아래 단계를 하나도 밟지 않고 blocked: "disabled"를 즉시 반환한다 — 체결 정산·잔액 반영·적립·주문 기록 중 어느 것도 실행되지 않고 lastRunDate도 갱신되지 않는다. 자세한 이유는 10장 참조.
  1. 체결 정산 — dryRun 정산과 LIVE 정산을 계좌 모드와 무관하게 항상 둘 다 돌린다(dry → live 순서). 정산 대상은 계좌가 아니라 주문 행의 dryRun으로 갈리고(dryRun: true, status: "simulated" ↔ dryRun: false, status: "submitted") 두 조건이 배타적이므로, 계좌 모드로 분기하면 모드를 토글한 뒤 남아 있던 행이 어느 정산도 받지 못해 얼어붙는다. dryRun 행은 tradeDate보다 이전인 simulated 주문을 그 날 일봉 + judgeDryFill로 판정해 simulated_filled / expired로 확정하고, LIVE 행은 getOrders(accountSeq, {status:"CLOSED", symbol, from})로 대조해 filled / expired로 확정한다. 둘 중 어느 쪽이 실패해도 blocked로 멈추고 다음 폴에서 재시도한다.
  2. 잔액 반영 — stateApplied가 아직 아닌 체결을 순수 함수 applyFills로 계산한 뒤, 그 델타만큼 cashKrw를 Prisma decrement로 차감하고 마커를 세운다. 그 실행에서 밀려 있던 체결 전체(account 업데이트 + 각 주문의 stateApplied)를 하나의 $transaction으로 묶어 원자 처리한다 — 주문마다 별도 트랜잭션이 아니다. 절대값 쓰기가 아니라 상대 증감이므로 동시에 다른 실행이 적립을 반영 중이어도 서로를 덮어쓰지 않는다.
  3. 적립 — lastAccrualDate !== tradeDate일 때만 순수 함수 accrue로 계산한 델타를 cashKrw에 Prisma increment로 더하고 같은 트랜잭션에서 lastAccrualDate = tradeDate로 갱신한다. 이후 단계가 보류되어도 재적립되지 않는다(10장 참조). 여기서도 절대값이 아닌 상대 증감을 써서 state.ts의 순수 함수가 계산의 유일한 근거로 남는다.
  4. peak 갱신 — base 종목의 전일 종가 prevClose가 peakPrice보다 크면 peakPrice/peakDate를 갱신. 전일 종가를 못 구하면 실패 사유를 담은 문자열(조회 자체가 실패했으면 전일 종가 조회 실패: ..., 조회는 됐지만 데이터가 없으면 전일 종가 미확보 — 재시도 대기)을 blocked·note에 그대로 남기고 보류(10장 참조).
  5. 종목 선택 — drawdown = prevClose / peakPrice - 1. drawdown ≤ -thresholdPct/100 + 1e-9이면 leverSymbol, 아니면 baseSymbol(허용오차는 4.3절 참조).
  6. 중복 방지 (1차) — 해당 계좌·거래일에 이미 주문 행이 있으면 아래 시세·환율 조회를 아예 건너뛰고 lastRunDate만 갱신한 뒤 종료한다. 네트워크 호출 전에 먼저 걸러 불필요한 왕복을 없앤다. 이 경로는 note를 지우지 않는다 — 직전 실행이 남긴 submit_unknown 경고가 다음 거래일에 조용히 사라지면 화면에 그 신호가 아예 남지 않는다.
  7. 주문 계산 — 선택 종목 현재가 p, 환율 fx에 대해 지정가 limit = round2(p × (1 + premiumPct/100)), 수량 qty = floor(cashKrw / fx / limit). qty < 1이면 주문 없이 종료(적립만 됨).
  8. LIVE 예수금 확인 — LIVE 계좌만. getBuyingPower(accountSeq,"USD")로 매수가능금액을 받아 !(buyingPower >= estUsd)로 판정한다(fail-closed). buyingPower < estUsd로 쓰면 응답 필드 누락·개편으로 NaN이 왔을 때 비교가 false가 되어 검사 없이 실주문이 나간다. 부족하거나 값이 유한하지 않으면 blocked + note로 보류하고 주문 행은 만들지 않는다 — 이 시점에 행이 없어야 같은 거래일 안에 다음 폴에서 재시도할 수 있다. 이 조회를 아래 재확인보다 먼저 두는 이유도 같은 맥락이다: 재확인과 주문 행 생성 사이에 네트워크 왕복이 끼면 중복 주문 창이 그만큼 다시 넓어진다.
  9. 중복 방지 (2차, 재확인) — 1차 체크 이후 시세·환율·예수금 조회(네트워크 왕복) 동안 동시 실행이 끼어들 여지가 있으므로, 주문 행을 만들기 직전에 같은 카운트를 한 번 더 실행한다. 걸리면 마찬가지로 lastRunDate만 갱신하고(note는 유지) 종료. 재확인 직후에 오는 것은 로컬 SQLite 쓰기 1회(주문 행 생성)뿐이므로 dryRun·LIVE 양쪽 모두 창이 그 한 번의 쓰기로 좁혀지지만, DB 제약은 아니다(12장 한계 참조).
  10. 기록 / 제출 — dryRun이면 status: "simulated" 행 1건을 만들고 끝. LIVE는 제출 전에 status: "submitting" 행을 먼저 만들어 그 행 자체를 뮤텍스로 쓰고, createOrder가 성공하면 같은 행을 status: "submitted" + tossOrderId로 갱신한다. 제출이 throw하면 실패로 단정하지 않고 status: "submit_unknown" + error로 남긴다(아래 블록쿼트). (kill switch는 이 단계 전에 이미 걸러진다 — 위 블록쿼트 참조)
  11. 정상 완료 경로는 lastRunDate = tradeDate, note = null로 마무리한다. 중복 방지 1·2차 경로는 lastRunDate만 갱신하고 note는 남겨둔다.
제출 실패는 "실패"가 아니라 "미확인"이다. tossFetch는 POST /api/v1/orders를 포함한 모든 호출에 10초 AbortSignal.timeout을 건다. 토스가 주문을 접수했는데 응답만 늦어도 submitOrder는 throw한다. 이때 failed로 기록하면 그 주문은 종가에 체결되는데 settleLiveOrders는 submitted만 조회하므로 영구히 정산되지 않고, cashKrw가 차감되지 않아 다음 거래일부터 부풀려진 잔액으로 계속 과매수한다(누적된다). 그래서 별도 상태 submit_unknown + error 문구를 남기고, 계좌 note에 주문 제출 결과 미확인 — 토스 앱에서 체결 여부를 직접 확인하세요: ...를 세워 카드에 경고 배지로 띄운다. lastRunDate는 갱신한다 — 여기서 자동 재시도하는 것이야말로 진짜 이중 매수를 만든다. 브로커 자동 대조는 하지 않는다: DcaRunDeps에 OPEN 주문 목록 조회가 없고, 추가하는 것은 이번 범위 밖이다.

12. 가정과 한계

  • 배당 재투자 미반영 — 백테스트는 수정주가를 썼지만 실운용은 현금 배당이 계좌에 쌓인다. QQQ 배당수익률 ~0.5% 수준의 괴리.
  • 기존 보유분은 교체하지 않는다 — 신규 적립금의 매수 종목만 바뀐다. 백테스트 조건과 동일.
  • peak 시딩의 한계 — 토스 200봉(약 10개월) 내 최고 종가만 확인 가능. 진짜 사상 최고가가 그 밖에 있으면 초기 낙폭이 과소평가되어 QLD 구간을 놓친다. 생성 폼에서 수동 입력으로 보정한다.
  • 종가 vs 수정주가 — peak과 낙폭 모두 토스 원종가 기준. 백테스트의 수정주가 기준과 미세하게 다르다.
  • 환율 근사 — 체결 차감액을 주문 시점 환율로 환산한다. 실제 원화 체결 원가와 소폭 차이.
  • 보유 정합성 대조 없음 — 같은 토스 계좌에서 다른 경로로 QQQ/QLD를 매매하면 화면의 보유수량(체결 이력 파생)이 실보유와 어긋난다. 주문 계산은 잔액만 쓰므로 주문 안전성에는 영향이 없다.
  • 적립 누락 보정 없음 — 워커가 꺼져 있던 거래일에는 적립이 일어나지 않고, 지난 거래일을 소급 적립하는 로직도 없다. 설정 폼에서 cashKrw를 직접 수정해 보정한다.
  • LIVE는 매수만 — 매도 경로가 없으므로 손절·익절은 수동이다.
  • 동시 실행 시 당일 중복 주문 가능성 (LIVE 전환 전 반드시 인지) — "지금 실행"은 Next 서버 프로세스에서, dca-loop는 별도 워커 프로세스에서 같은 SQLite 파일에 붙는다. 같은 거래일 중복 주문 방지는 여전히 count 후 create이고(6장 참조) 데이터베이스 제약(@@unique)은 아니다. 다만 창의 폭은 줄었다: LIVE 경로도 제출 전에 주문 행을 먼저 만들도록 바꿨고(submitting) 예수금 조회를 재확인보다 앞으로 옮겼기 때문에, 재확인과 행 생성 사이에 남는 것은 dryRun·LIVE 모두 로컬 SQLite 쓰기 1회뿐이다(이전에는 LIVE만 getDefaultAccountSeq + getBuyingPower + createOrder 세 번의 네트워크 왕복 뒤에 행이 생겨 창이 수백 ms 이상이었다). 그래도 두 실행이 그 한 번의 쓰기 사이에서 정확히 겹치면 같은 거래일에 주문 두 건이 만들어질 수 있다.
  • cashKrw 절대값 쓰기 (남은 위험은 좁아졌다) — updateDcaSettings는 cashKrw·peakPrice를 절대값으로 덮어쓰는 반면 runDca는 상대 증감(increment/decrement)만 쓴다. 설정 폼은 마운트 시점의 문자열을 useRef로 보관하고 사용자가 실제로 고친 필드만 patch에 담으므로(updateDcaSettings는 undefined 키를 건너뛴다), 폼을 열어둔 사이 워커가 반영한 적립·체결 차감·peak 갱신이 손대지 않은 필드의 옛 스냅샷으로 덮이는 일은 없다. 남은 위험은 사용자가 의도적으로 잔액을 보정해 저장하는 그 순간에 실행이 겹치는 경우뿐이다 — 이때는 절대값 쓰기가 그 사이 반영된 증감을 덮는다. 잔액 보정은 정규장 밖(워커가 실행하지 않는 시간)에 하는 것이 안전하다.
  • 후속 과제: @@unique([accountId, tradeDate]) — 중복 주문의 근본 해결은 여전히 DcaOrder에 이 복합 유니크 제약을 걸고 위반을 우아하게 처리하는 것이다. 최종 리뷰에서 모든 코드 경로가 계좌·거래일당 정확히 1행만 만든다는 점을 확인했으므로(정상 흐름을 깨지 않는다) 권장 후속 작업이다. 이번 범위에서는 마이그레이션을 만들지 않았다.
  • 미해결 제출 상태는 사람이 닫아야 한다 (LIVE 전환 전 반드시 인지) — 주문 이력에 submit_unknown(제출이 throw — 타임아웃이면 브로커는 접수했을 수 있다) 또는 submitting(제출 도중 프로세스 중단)이 보이면, 토스 앱에서 그 거래일의 실제 체결 여부를 직접 확인해야 한다. 체결됐다면 그 주문은 자동 정산 대상이 아니므로(settleLiveOrders는 submitted만 본다) 설정 폼에서 cashKrw를 체결금액만큼 직접 줄여야 하고, 그러지 않으면 다음 거래일부터 부풀려진 잔액으로 계속 과매수한다. 계좌 카드의 경고 배지(note)는 이후 정상 실행이 note = null로 덮으므로, 지속되는 기록은 주문 이력의 상태값이다. 브로커 대조 자동화(OPEN 주문 조회)는 DcaRunDeps에 없고 이번 범위 밖이다.
  • 시뮬레이션 → LIVE 전환 후의 잔액 괴리 — 정산은 계좌 모드가 아니라 주문 행의 dryRun으로 갈리고 항상 둘 다 돌기 때문에, LIVE로 전환한 계좌도 남아 있던 시뮬레이션 체결분을 cashKrw에서 차감한다(내부적으로는 일관된 선택이다 — 그 종이 주문도 잔액을 배정받아 만들어졌다). 반면 보유·평가액 표시는 현재 모드와 같은 행만 집계하므로 그 종이 체결은 화면에서 사라진다. 결과적으로 전환 직후 추적 잔액이 실제 증권계좌 현금과 어긋날 수 있다. 리셋 로직은 넣지 않았다 — 전환 전에 시뮬레이션 주문을 모두 정산시키고(하루 이상 실행) 필요하면 설정 폼에서 cashKrw를 실제 예수금에 맞춰 보정할 것.
