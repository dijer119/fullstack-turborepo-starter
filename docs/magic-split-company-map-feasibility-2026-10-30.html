매직스플릿 분할매수·분할매도
company-map 구현 가능성

판정: Trial 핵심 로직은 구현 가능하다. 차수별 장부와 모의 실행부터 추가하는 방향을 권고한다.

company-map에는 이미 토스증권 시세·잔고·주문 클라이언트와 전략별 worker, 주문 이력, dry-run 테스트 구조가 있다. 새 증권사부터 연결할 필요는 없다. 다만 무한매수법·VR의 전략은 종목 전체 평단과 보유량 중심이므로, 매직스플릿의 독립 차수 관리와 장중 반복매매를 그대로 맡길 수는 없다.

실거래는 추가 작업이 큰 부분이다. 차수별 체결 귀속, 중복 실행 방지, 부분체결 증분 반영, 현금·수량 예약, 미체결 취소와 복구가 필요하다. 기존 코드의 존재만으로 안전한 장중 실거래가 검증됐다고 볼 수 없다.

제품 로직 근거: 공식 자동매매 설정 · 모바일 차수별 주문 안내. 프로젝트 근거는 아래 파일·행을 명시했다. 이번 작업은 검토와 문서 작성이며 앱 코드·DB·운영 worker는 변경하지 않았다.

구현할 규칙현재 코드와 차이증권사 제약추가 구조실행 방식검증 기준권장 범위근거와 한계

1. 구현 대상은 ‘차수별 독립 매매’

공식 설명의 핵심은 설정한 하락 구간에서 추가 매수하고, 각 매수 차수의 수익률로 해당 물량을 매도하는 것이다. 예를 들어 1차 10,000원, 2차 9,000원, 3차 8,100원에 샀다면 8,910원에서 3차만 이익 매도할 수 있다. 전체 평단이 회복될 때까지 기다리는 구조와 다르다. 차수별 매수·매도 예시

증권사에는 같은 종목의 합산 수량이 존재한다. 어떤 차수의 수량을 팔았는지는 우리 앱의 내부 장부가 배분한다. 따라서 실제 계좌의 보유 수량과 내부 차수별 수량을 함께 맞추는 것이 구현의 중심이다. 차수별 전략 손익은 증권사가 표시하는 평균단가 손익이나 세무 계산과 구분해야 한다.

공개 자료로 확인한 것과 우리가 정할 것을 구분

항목 공개 설명으로 확인 구현 시 명시해야 하는 정책
추가 매수 차수별 매수 간격·금액·최대 차수를 설정한다. 기준 차수의 실제 체결가를 쓸지, 첫 매수 기준 고정 가격표를 쓸지. 갭 하락 때 여러 차수를 한꺼번에 살지도 정해야 한다.
익절 차수별 목표 수익에 도달하면 해당 차수를 판다. 가격 수익률과 비용 차감 후 수익률 중 무엇을 기준으로 할지, 호가 반올림과 부분매도 배분을 정해야 한다.
재매수 매도한 하위 차수를 다시 매수하는 설명이 있다. 공식 개념 상위 차수의 기준가를 유지할지, 상위가 먼저 매도됐을 때 어떻게 할지, 재진입 이력을 어떻게 구분할지 정해야 한다.
전량 청산 후 수익부스터가 1차 재진입 감시를 지원한다. 공식 기능 자동 재시작 여부와 새 사이클 예산. 최초 버전은 정지 후 사용자가 새 사이클을 시작하는 방식이 단순하다.
장부 재구성 리스플릿은 매입금액을 유지하며 차수를 재배분한다. 공식 설명 원가·이력 변경의 감사 추적이 필요하다. 핵심 분할매매와 분리해 후속 범위로 두는 것이 낫다.

동일한 매매 원리를 독자적으로 구현할 수 있다는 판단이다. 공개 매뉴얼만으로 상용 제품의 모든 경계 동작·체결 결과와 완전히 같다고 보장할 수는 없다. 아래 제안은 제품 내부 알고리즘을 확인한 명세가 아니다.

첫 버전에서 검증할 수식 예시 — 제안

추가 매수 감시가 = 기준 차수의 확정 매수단가 × (1 − 매수 간격 / 100)
차수별 매도 감시가 = 해당 차수의 실제 매수단가 × (1 + 익절률 / 100)
매수 수량 = floor(차수 예산 ÷ 실제 주문 지정가)   // 정수주 버전

미체결 주문의 수량과 금액은 사용 가능 수량·예산에서 예약 차감한다.
장부는 주문 접수 시점이 아니라 실제 체결 증분으로 갱신한다.
수수료·세금·호가 단위 반영은 감시가 계산과 별도 규칙으로 둔다.

위 수식은 이해를 위한 초안이다. 매수 간격과 익절률의 기본값을 추천하는 것은 아니며, 재매수의 기준 차수·기준가격은 주문 생성 당시 저장해 이후 가격 변화로 조용히 바뀌지 않게 해야 한다.

3. 실거래를 좌우하는 토스 API 제약

국내주식은 반대 방향 일반주문을 동시에 쌓을 수 없다

현재 공식 FAQ는 국내주식에서 같은 종목의 반대 방향 미체결 일반주문이 있으면 가격이 겹치지 않아도 409 opposite-pending-order-exists로 거절한다고 명시한다. 미국주식에는 이 제한이 적용되지 않고, 조건주문 등록·발동에도 이 사유는 적용되지 않는다고 설명한다. 공식 FAQ

설계 영향: 국내주식의 모든 차수에 매수·매도 지정가를 미리 동시에 제출하는 방식은 채택하기 어렵다. 앱에서 조건을 감시하다 제출하고 종목별 미체결 방향을 조정하거나, 증권사 조건주문을 별도로 검토해야 한다. 취소 요청 직후 반대 주문을 보내면 체결과 취소가 경합할 수 있으므로, 최종 상태와 누적 체결량을 확인하는 단계가 필요하다.

실시간 감시는 가능하지만 새 연동이 필요하다

현재 공식 문서는 WebSocket 시세·주문 이벤트와 조건주문을 제공한다. 오래된 검색 캐시의 “REST만 제공” 문구 대신 조사일의 렌더링된 공식 문서와 Context7의 공식 문서 발췌를 대조했다. 기존 company-map 클라이언트에서는 WebSocket·조건주문 래퍼를 찾지 못했다. 현재 공식 API · 주문 이벤트

WebSocket의 주문 이벤트 보장은 연결 세션 내부에 한정된다. 끊긴 구간의 이벤트는 재전송되지 않으므로 재연결 후 REST 주문 대조가 필요하다. 현재 안내 한도는 계정당 동시 연결 2개, 연결당 구독 합계 100건이다. 시세·호가·계좌 구독이 각각 공간을 차지하므로 차수마다 연결을 만들면 안 된다. 연결·구독 규칙 · 재연결 규칙

현재 주문 조회를 고빈도 매매에 그대로 쓰면 누락될 수 있다

공식 FAQ는 종료 주문 목록을 한 번에 최대 100건 반환하고 cursor로 이어 조회한다고 안내한다. 현재 fetchOrdersWindow는 orders만 읽고 커서를 처리하지 않는다. 날짜 구간 분할은 있지만 같은 구간 안의 페이지 순회는 없다. 따라서 그 구간에 종료 주문이 100건을 넘는 경우 모든 체결을 확보한다고 보장할 수 없다. 고빈도 전략을 추가하기 전에 보강할 부분이다. 조회 한도 · 현재 조회 구현:558

주문 결과 미확인과 부분체결은 별도로 다뤄야 한다

  • 멱등키는 영구 중복 방지가 아니다. 공식 clientOrderId 유효기간은 10분이다. 타임아웃 후 10분을 넘겨 같은 키로 재전송하면 새 주문이 될 수 있다. DB에 주문 의도를 영속화하고 결과 미확인 상태에서는 대조 없이 새 주문을 내지 않아야 한다. 공식 주문 생성
  • 체결은 누적값으로 제공된다. REST는 주문별 누적 체결 수량과 평균가를 반환한다. 기존 무한매수 동기화는 CLOSED 주문만 다루고 양수 체결을 filled로 저장한다. 장중 OPEN 부분체결과 추가 체결량을 차수 장부에 반영하는 새 경로가 필요하다. 공식 체결 조회 · 현재 동기화:94
  • 소수점 주문은 후속 범위가 적절하다. 기존 DCA의 금액 기반 매수는 미국 MARKET 전용이며, 지정가 수량 주문과 요청 형태가 다르다. 첫 버전은 한 시장·정수주로 한정하면 차수 잔량과 주문 방식을 일관되게 만들기 쉽다. 현재 요청 타입:453 · 공식 주문 규칙

위 API 지원은 문서상 확인이다. 해당 계정의 실제 WebSocket 연결, 조건주문 등록 가능 여부, 권한·세션별 동작은 이번에 실행하지 않았다. 증권사 고유 제약은 해당 증권사 공식 자료가 기준이며, 다른 제공자의 문서를 독립 검증으로 간주하지 않았다.

4. 추가해야 할 최소 데이터 구조 — 제안

기존 InfiniteBuyCycle을 다른 의미로 재사용하기보다 별도 전략 상태를 추가하는 편이 낫다. 무한매수법의 T·round·미국 거래일과 매직스플릿의 반복 차수는 의미가 다르다. 아래 이름은 검토용이며 실제 스키마를 추가한 것은 아니다.

제안 모델 저장할 내용 필요한 이유
SplitStrategy 계좌, 종목, 시장·통화, 예산, 최대 차수, 간격, 목표, 실행 모드, 상태, 설정 버전 같은 기준으로 시세 판정과 장부 재현. 모의와 실거래의 자산을 분리한다.
SplitLot 슬롯 번호, 재진입 회차, 기준 차수·기준가, 실제 원가, 매수량, 잔여량, 비용 차수별 독립 익절·재매수와 과거 이력을 동시에 관리한다.
SplitOrder 차수 귀속, 매매 방향, 영속 주문 의도키, clientOrderId, broker ID, 상태, 요청값, 적용한 누적 체결량·금액·비용 재시작·응답 유실·부분체결을 복구하고 같은 체결을 두 번 적용하지 않는다.
예약·소유권·실행 잠금 계좌·통화별 예약 현금, 종목별 예약 수량, 전략 소유권, 만료·세대가 있는 실행권 동시 전략·수동 실행·중복 worker가 같은 돈이나 물량을 중복 사용하지 못하게 한다.

돈과 가격은 시장별 고정 소수 단위를 정의하고, 호가·정수 수량 계산을 전략 경계에서 수행해야 한다. 전략별 자금 예약과 실제 브로커 매수가능금액은 별개 제약이다. 브로커가 이미 미체결 자금을 제외한 응답을 주는지 확인하고 우리 예약액을 이중 차감하지 않도록 해야 한다.

상태 전이는 체결에 따라 진행

빈 차수
  → 매수 의도 저장·예산 예약
  → submitting → submitted → partial → filled
  → 차수 보유
  → 매도 의도 저장·수량 예약
  → submitting → submitted → partial → filled
  → 차수 종료·예약 해제·다음 재진입 회차 준비

취소·거절: 최종 체결량 대조 후 남은 예약 해제

부분체결 증분 계산 예시

처음 누적 2주·평균 100원에서 나중에 누적 5주·평균 106원이 됐다면, 추가 반영분은 3주·330원이다. 새 평균 106원에 추가 3주를 곱하면 318원으로 잘못 계산된다. 가능하면 API 누적 체결금액의 차이를 사용하고, 잔량·원가·현금을 한 트랜잭션에서 갱신해야 한다. 

추가 체결량 = 새 누적 체결량 − 이미 적용한 누적 체결량
추가 체결금액 = 새 누적 체결금액 − 이미 적용한 누적 체결금액
예시: 5 × 106 − 2 × 100 = 330

매수: 차수 잔량 증가, 실제 비용 증가, 예약 현금을 체결분만큼 전환
매도: 해당 차수 잔량 감소, 귀속 원가·비용으로 실현손익 계산

5. 감시·주문 실행 방식 비교

방식 장점 제약·판단
기존 15분·일일 실행 유지 추가 작업이 적다. 장중 가격 왕복을 놓친다. 무한매수·DCA를 그대로 유지하는 대안은 유효하지만 매직스플릿 구현으로 부르기는 어렵다.
별도 worker에서 직접 감시 차수 정책·거래시간·주문 순서를 앱이 통제한다. 기존 순수 코어/어댑터 패턴과 맞는다. 권장 출발점. 모의 실행은 저장된 시세 재생으로 검증한다. 실시간화는 WebSocket과 REST 복구를 결합하거나, 소수 종목의 주기 조회로 시작할 수 있다. 조회 방식의 순간 가격 누락은 명시해야 한다.
증권사 조건주문 활용 가격 감시를 증권사에 맡길 수 있고 국내 반대 방향 일반주문 제약과도 다르게 취급된다. 조건주문은 별도 수명·취소·체결 매핑이 필요하다. 장 선택 불가, 그룹 조건 제한, 유효기간·수량·세션 동작을 확인한 뒤 채택한다. 최초 버전의 전제 조건으로 둘 필요는 없다.

외부 근거: 일반주문·조건주문 차이와 세션 선택 제약, 조건주문 타입. 위 비교는 프로젝트 적합성에 대한 판단이며 주문을 등록한 결과가 아니다.

시나리오 통과 기준
기본 하락·반등 10,000 → 9,000 → 8,100 → 8,910의 순차 입력에서 설정에 맞는 매수만 발생하고, 10% 익절인 3차만 매도한다.
매도 후 재진입 8,100원 기준의 3차를 청산 후 다시 8,100원에 도달하면 재진입 정책에 따라 1회만 매수한다. 1·2차의 원가와 잔량은 보존된다.
다중 worker·수동 동시 실행 동일 신호를 동시에 처리해도 DB 주문 의도는 하나이며 브로커 제출이 중복되지 않는다. 실행권 만료 후 옛 worker도 새 주문을 못 낸다.
타임아웃·재시작 접수 여부 불명 주문을 unknown으로 남기고 대조한다. 브로커 멱등 기간 이후 맹목 재전송하지 않는다.
부분체결·취소 경합 누적 체결량·금액의 차이만 반영한다. 취소 직전 체결도 반영하고 미체결 잔량에 해당하는 예약만 해제한다.
국내 반대 주문 미체결 일반주문과 새 방향의 충돌을 감지하고, 취소·종료·잔고 대조 후 순서대로 실행한다.
데이터 단절·조회 101건 이상 시세·연결 이상 시 새 주문을 보류한다. 재연결 후 대조하며 커서 뒤에 있는 체결도 모두 반영한다.
예산·수량 보존 차수 잔량 합계와 귀속 보유량이 일치한다. 모든 미체결 예약을 포함해 현금·매도 가능 수량을 초과하지 않는다.
모의·실거래 분리 모의 차수·예수금·체결을 LIVE로 승계하지 않는다. 전환 시 실제 보유량과 전략 초기 잔고를 명시적으로 대조한다.
