#발견한 결함과 결정틀렸을 때 비용
P1계획의 pickSymbol에 실제 결함. IEEE754로 90/100-1 = -0.09999999999999998이라 ratio <= -0.1이 false → 계획 자신의 "정확히 임계값이면 레버리지" 테스트를 통과할 수 없었음. 제 pre-flight 스캔이 수학적으로만 검산해 놓친 것. 스펙 §4.2가 "경계 포함"을 명시하므로 스펙을 권위로 삼아 1e-9 epsilon 승인(표시 반올림 경계 케이스의 간격 ~4e-5보다 4자리 작아 두 테스트 공존)실제 낙폭이 임계보다 1e-9 이내로 얕은 순간에 레버리지 판정 — 가격 정밀도상 관측 불가
P4킬스위치가 정산 불가능한 주문 행을 만듦. 정산 분기는 계좌의 dryRun으로 갈리는데 killed 기록은 dryRun:true+simulated로 씀 → LIVE 계좌는 settleLiveOrders만 타므로 아무도 정산하지 않고, 그 계좌를 dryRun으로 되돌리면 +5% LOC로 거의 확실히 체결 판정돼 사지도 않은 주식 값이 실제 잔액에서 차감. 형제 run-vr.ts 관행대로 killed면 아무것도 하지 않고 blocked: "disabled"로 조기 반환 — 고아 행이 구조적으로 불가능하고 킬스위치 해제 시 재시도됨킬스위치가 걸린 날의 dryRun 시뮬레이션 연속성이 한 거래일 끊김

P3"일봉 200봉을 런당 최대 4회 중복 fetch" 지적 — 규모를 직접 계산해 전제가 틀렸음을 확인: peak 시딩은 runDca 안이 아니라 계좌 생성 시에만, settleDryOrders는 이미 Map 캐시 보유, runDca는 거래일당 계좌당 1회. 실제 중복은 계좌당 거래일당 1회계좌당 거래일당 토스 200봉 요청 1회 추가
P9두 폼이 각자 독립 useTransition을 써서 설정 저장 중에도 "지금 실행" 버튼이 활성 — VrManager.tsx도 동일한 기존 하우스 패턴이고 계획 제약이 "기존 패턴을 따르고 고장나지 않은 것을 리팩터링하지 말 것"을 요구. 다만 이 판정이 근거로 든 "실제 위험"은 FR1로 별도 해결됨설정 저장과 "지금 실행"을 겹쳐 누르면 수동 잔액 보정이 덮어써질 수 있음
FR5accountSeq 미사용 컬럼(스펙이 "null=기본계좌"로 설계한 필드, 실제 계좌 표시는 기능 요청) / getClosedOrders의 limit 100(무한매수법은 TQQQ·SOXL을 거래해 심볼이 겹치지 않음)돈이 빠져나가는 계좌가 화면에 표시되지 않음; 같은 심볼을 다른 경로로 대량 거래하면 대조 대상이 100건 밖으로 밀려 조용히 미정산

4. 검증된 것과 검증되지 않은 것

검증됨

  • 테스트 343건 전부 통과(43파일). 신규 5파일 49건 — 순수 함수 33 + 오케스트레이터 16.
  • 오케스트레이터 테스트가 실제로 증거가 되는지 회의적으로 검증됨: fake의 dcaAccount.update가 Prisma의 {increment}/{decrement}를 실제로 해석하며 미지원 연산자엔 throw(무시하면 모든 cashKrw 단정이 무의미해짐), 차감 단정이 정확한 수치를 못 박음, "create가 submit보다 먼저"를 스텁 안 스냅샷으로 실제 순서를 관측, 멱등 케이스가 lastRunDate만 리셋해 단정이 자동으로 참이 되지 않음.
  • 실DB 스모크 — 같은 거래일 2회 실행에 적립·주문 중복 없음. 임시 계좌 삭제 확인, 양 테이블 0행.
  • tsc --noEmit exit 0, 변경 파일 lint 에러 0.
  • 17개 커밋 전부 경로 명시 — 사용자의 무관한 미커밋 변경 9건이 세션 시작과 동일하게 보존됨.

검증되지 않음

  • 브라우저 렌더링 — dev 서버의 stale PrismaClient 때문에 /stocks/dca가 500. 1장의 육안 확인 6가지가 그래서 남아 있습니다.
  • 실제 주문 제출 — 검증 중 실주문을 넣지 않는다는 제약을 지켰으므로, LIVE 경로의 근거는 fake db 테스트 4케이스 + 코드 판독입니다.

5. 남은 후속 과제 (LIVE 전환 전 검토)

우선항목왜 남겼는가
열림(중간)@@unique([accountId, tradeDate])이전 버전의 "폐기" 판단은 틀린 근거에 기대고 있었습니다. "submit_unknown 이후 같은 키로 재시도하는 것 자체가 복구 메커니즘"이라고 적었지만 코드에 그런 경로가 없습니다 — submit_unknown이면 lastRunDate가 소진되고, 그걸 지워도 당일 주문 수 가드가 already_ordered로 막습니다(같은 표의 바로 아래 행이 말하는 "자동 대조 없음, 사람이 확인"과도 모순이었습니다). 실제로 맞는 서술은 이렇습니다: 동시 제출은 토스가 clientOrderId(dca-<계좌 앞 16자>-<거래일>, 결정적 생성, 10분 유효)로 한 브로커 주문에 합쳐 주고, settleLiveOrders가 소비된 tossOrderId를 추적해 합쳐진 쌍이 두 번 차감되는 것도 막습니다. 그래서 DB 제약은 필수가 아니지만 유해하지도 않습니다. 현재 모든 코드 경로가 계좌·거래일당 정확히 1행만 만들므로 제약을 걸어도 정상 흐름이 깨지지 않습니다(이번 웨이브에서 마이그레이션은 실행하지 않았습니다). 참고로 소비된 tossOrderId 집합은 계좌 범위라 계좌 간 앞 16자(64비트) 충돌은 막지 못합니다
높음미해결 주문 해소 UI위 차단을 앱 안에서 풀 수단이 없습니다. 주문 이력 행에 "체결로 확정"·"미체결로 종료" 버튼만 있어도 prisma studio 없이 해소됩니다. 무인 운용 전략에서 제출 타임아웃 한 번이 계좌를 무기한 멈추므로 이것이 최우선입니다.
높음submit_unknown 행의 자동 대조제출 응답이 10초를 넘긴 주문. 현재는 상태+note로 사용자에게 보이게만 했고, 자동 대조는 DcaRunDeps에 OPEN 주문 조회가 없어 범위 밖. 이 상태가 보이면 토스 앱에서 체결 여부를 직접 확인하세요. 이제 이런 행(submitting·submitted·submit_unknown)이 이전 거래일에 남아 있으면 runDca가 적립만 하고 신규 주문을 막습니다 — 안전 방향이지만, 상태를 바꾸는 UI가 없어 해소하려면 prisma studio로 dca_orders 행을 직접 고쳐야 합니다. 해소 방법이 두 가지인데 두 번째가 낫습니다: ① status를 expired로 바꾸고 cashKrw를 손으로 맞추거나, ② 토스 앱에서 실제 체결 내역을 확인해 그 행에 status: "filled" + 실제 filledQty·filledPrice를 넣고 stateApplied는 null로 두는 것. ②는 다음 실행의 applyPendingFills가 주문에 저장된 환율로 알아서 차감하므로 원화를 손으로 계산할 필요가 없고 "잔액 먼저 보정" 순서 함정도 없습니다.

주의 1 — 계좌를 dryRun으로 되돌려도 이 차단은 풀리지 않습니다. 가드가 계좌가 아니라 주문 행의 dryRun을 보기 때문입니다. "일단 안전하게 시뮬레이션으로 돌려두자"가 가장 자연스러운 대응인데 그 방법으로는 안 풀립니다 — 행을 고쳐야 합니다.
주의 2 — 차단 중에도 적립은 매 거래일 계속됩니다. 사이징에 상한이 없으므로, 2주를 모르고 지나간 뒤 차단을 풀면 그날 한 번에 누적 잔액 전액이 시장가로 매수됩니다. 풀기 전에 cashKrw를 의도한 크기로 줄일지 판단하세요.
주의 3 — submitted 행은 정산이 영영 못 고치는 이유로 남을 수 있습니다(계좌 accountSeq 변경, 또는 주문이 getOrders의 CLOSED 100건 페이지 밖으로 밀려남).
해결됨테스트 픽스처 2건 보강수량은 이미 0.05로 1이 아니고, 환율은 run-dca.test.ts의 "차감에는 주문 행의 fxRate를 쓴다" 케이스가 주문 환율 1,200 / 정산일 환율 1,500을 다르게 두고 결과를 고정합니다 — 구현이 정산일 환율로 바뀌면 실패합니다(제거 검증 완료)
중간fake db의 matches를 미지원 연산자에 throw로현재 {lt}·{in}·OR·스칼라만 처리하고 그 외 조건은 조용히 전건 일치. where 조건을 하나 더 붙이면 필터가 무력화되고 테스트는 계속 초록으로 남는 유지보수 함정
낮음tossFetch의 401 재시도가 POST /api/v1/orders에도 적용"행이 뮤텍스" 논리 밖의 유일한 재제출 경로. 401은 인증 실패라 주문이 생성되지 않았을 것이므로 실무상 무해하나, 주문 엔드포인트만 재시도에서 빼는 것을 검토할 만함. 토스 클라이언트 공용 코드라 무한매수·VR도 함께 영향받으므로 이 브랜치 범위 밖
낮음워커 미가동 거래일의 적립 누락소급 적립 로직 없음. 설정 폼에서 cashKrw를 수동 보정하세요(FR1 수정 덕분에 이제 의도적으로 편집한 필드만 저장됩니다)

6. 알아두실 구조적 한계

  • 배당 재투자 미반영 — 백테스트는 수정주가를 썼지만 실운용은 현금 배당이 계좌에 쌓입니다. QQQ 배당수익률 ~0.5% 수준의 괴리.
  • peak 시딩은 200봉(약 10개월)까지만 — 토스 일봉 API 상한. 사상 최고가가 그 밖에 있으면 초기 낙폭이 과소평가되므로 생성 폼에서 직접 입력하세요.
  • 화면 판정 근거가 워커와 다름 — 화면은 현재가, 워커는 전일 종가로 낙폭을 계산합니다. 세 타일 모두 "(현재가 기준)" 캡션을 달아 구분했습니다.
  • 시뮬→LIVE 전환 후 잔액 괴리 — LIVE 계좌도 남은 시뮬레이션 체결의 차감을 흡수하므로(장부 내부 정합성 선택) 추적 잔액이 실제 브로커 현금과 일치하지 않습니다. 보유수량은 계좌 모드에 맞는 체결만 집계합니다.
  • 매도 경로 없음 — 손절·익절은 수동입니다.
  • 체결가는 종가가 아니라 장중 시장가 (금액 기반 전환 이후) — orderAmount는 MARKET 전용이라 timeInForce: "CLS"(종가매수)와 공존할 수 없다. peak·낙폭 판정은 여전히 전일 종가를 쓰지만, 실제 매수 가격은 그날 실행 시점의 장중 시세다. 방향성 없는 잡음이라 누적으로는 상쇄될 것으로 기대하나, 개별 거래일 단위로는 백테스트가 가정한 종가 체결과 괴리가 있다. 단서: 워커는 프로세스 시작 시각 기준 15분 고정 간격으로 폴하고 창 판정이 개장 순간을 포함하므로, 실제 체결은 사실상 매일 개장 후 0~15분에 몰린다. 스프레드가 가장 넓고 변동성이 큰 구간이라 "방향성 없는 잡음" 기대는 장 초반에서 덜 성립한다.
  • 금액 기반 주문 접수 창 (금액 기반 전환 이후) — 정규장 시작부터 종료 1시간 전까지만 접수된다. 창이 닫히면 그날은 적립만 반영되고 lastRunDate가 소진된다. 캘린더 조회 자체가 실패하면 "닫힘"과 구분해 재시도 대기로 남긴다. 창 확인 이후에도 시세·환율·예수금 조회가 끼어 있어 마감 직전 토스가 422 amount-order-outside-regular-hours로 거절할 수 있는데, 그 결과는 이제 status: "rejected" + "창 닫힘" 안내로 기록된다(시차 자체는 그대로).
  • 브로커의 "확실한 거절"은 사람 확인 대상이 아니다 (이번 웨이브) — 토스가 HTTP 400/422로 되돌려준 응답은 주문이 만들어지지 않은 것이 확정이라 status: "rejected"로 적고 cashKrw도 건드리지 않는다. 타임아웃·401·403·5xx·429는 주문이 생겼을 수 있으므로 보수적으로 submit_unknown을 유지한다.
  • 실행 1회당 캘린더를 두 번 받는다 — 워커의 세션 확인과 runDca ⑥의 창 확인이 같은 캘린더를 각각 조회한다(src/가 worker/를 import하지 않는 관행 탓에 판정이 복제돼 있다). 토스는 클라이언트당 활성 토큰이 1개뿐이라 이 여분의 호출이 토큰 재발급 경합을 늘리고, 곧 제출이 10초 타임아웃에 걸릴 확률(→ submit_unknown)을 높인다. 고치려면 캘린더를 DcaRunDeps로 흘려보내야 한다.
  • 이 브랜치의 마이그레이션은 비어 있지 않은 테이블에 재적용할 수 없다 — 20260827221805_dca_amount_based_orders의 INSERT ... SELECT에 NOT NULL인 amount_usd가 빠져 있다. 이미 적용된 현재 DB에는 무해하고, 마이그레이션 이전 백업을 복원해 다시 적용할 때만 실패한다.
  • 토스 buying-power(USD)는 원화 잔고를 반영하지 않는다 (2026-08-30 실측) — 원화 10,000원을 입금하니 currency=KRW는 ₩7→₩10,007로 정확히 늘었으나 currency=USD는 $6,870.63에서 1센트도 움직이지 않았다. DCA의 예수금 가드는 getBuyingPowerUsd 하나만 보므로(src/lib/dca/toss-deps.ts), 자금 보충 시 달러 환전까지 마쳐야 한다. 원화만 입금하면 매 거래일 USD 예수금 부족으로 보류되면서 cashKrw 적립만 쌓이고, 나중에 환전한 순간 누적 전액이 한 번에 시장가로 나간다(사이징에 상한이 없다). 가드를 currency=KRW로 바꾸는 것은 해법이 아니다 — 주문은 orderAmount를 USD로 보내므로 체크만 통과하고 브로커가 422 insufficient-buying-power로 거절하는 fail-open이 된다. 유보: 이 API에 안 잡힌다는 것이 토스가 주문 시 원화를 쓸 수 없다는 증명은 아니다(통합증거금 가능성). 그렇다면 현행 가드는 살 수 있는데 안 사는 보수적 방향으로 틀리는 셈이나, 달러로 채워두면 어느 쪽이든 무관하다.
